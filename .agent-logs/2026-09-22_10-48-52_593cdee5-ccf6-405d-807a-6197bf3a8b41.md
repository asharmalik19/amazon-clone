Phase 11 (Authentication) is implemented, tested, merged to `main`, and live.

**What landed**

- `app/models.py` — `User` (normalized unique email, name, bcrypt `password_hash`, `created_at`). `Cart.user_id` stays an unconstrained integer: with no migration tool, a FK would describe a schema production doesn't have. Phase 12 starts writing it.
- `app/security.py` — bcrypt hashing, the credential check, email/name/password rules, and the signed session cookie (user id + issue time, httpOnly, `Secure` from the same setting the cart cookie reads, 30-day window **enforced server-side**). The cart cookie's HMAC moved here too, so both cookies share one verifier and one reject path — Phase 10's bytes-not-`str` hardening now covers the session cookie by construction.
- `app/routers/auth.py` — `GET/POST /signup`, `GET/POST /signin`, `POST /signout` (no `GET`). Success is a 303; every failure is the same form again, 400, with the values kept and the passwords never echoed. Sign-in gives one identical message and the same hashing time for a wrong password and an unknown address, so the form can't be used to enumerate accounts.
- Templates — Amazon-styled `signin.html`/`signup.html`, a shared labelled-field macro, and `account_menu.html` in the header driven by `current_user` from `shell()`. The `account` feature flag flipped; no header control is a placeholder any more.
- `tests/test_auth.py` — 60 tests: the signup→signout→signin journey, every form refusal, and the cookie attacked the way Phase 10 attacked the cart's (forged, truncated, expired, re-signed, naming a deleted account, arbitrary bytes). Suite: **342 passed**, `ruff check` clean.

**Two things worth flagging**

1. `tech-stack.md` specified `passlib[bcrypt]`; passlib has had no release since 2019 and its bcrypt backend breaks against bcrypt 4.x. I used `bcrypt` directly and updated the spec's row and reasoning rather than departing from it silently.
2. `verify_password` now validates the shape of a stored hash before calling bcrypt — a truncated digest *panics* inside bcrypt's Rust extension, and `PanicException` isn't an `Exception`, so it would have escaped the route as a 500. A test covers it.

**Verified live** at <https://amazonia-jpu0.onrender.com> — signed-out header, rejected signup with all three messages, signup → greeted by name, duplicate refused, signout, wrong password refused, signed back in. The production cookie carries `HttpOnly; Secure; SameSite=lax; Max-Age=2592000`. Accounts sit in managed Postgres, so they survive redeploys.

The local app is still running on <http://127.0.0.1:8000> with the browser tab left on the signed-in home page for you to look at.
